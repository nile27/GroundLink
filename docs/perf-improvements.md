# 성능 개선 단계별 결과

기준선(`docs/perf-baseline.md` "새 기준선 (v2)")과 같은 조건에서 개선을 하나씩 적용하고 다시 쟀다.

- 측정: `bench/run.mjs`, 단계마다 빈 테이블(`RESET=1`), 각 180초, 서버는 단계마다 새로 시작
- 환경: M1 / 8 GiB, Docker Desktop CPU 8 · 3.83 GiB, PostgreSQL 17.11 기본 설정, pg 풀 10
- 지연은 **수신→커밋 완료** (서버가 INSERT 커밋 직후 잰 값, `/metrics/ingest`)
- 원본: `bench/results/` (git 제외). 폴더 이름의 라벨: `baseline2`, `A-batch`, `AB-drop-oldest`, `AB-drop-newest`

## 개선 A: 텔레메트리 일괄 저장

### 무엇을 바꿨나
- 텔레메트리를 메모리 버퍼에 모았다가, `BATCH_SIZE`(500)건이 차거나 `FLUSH_MS`(200 ms)가 지나면(먼저 오는 쪽) 다중 행 INSERT 1건으로 저장
  - TypeORM `repository.insert(rows[])` 사용. DB 전용 문법 없음
- 동시에 진행하는 저장은 풀 크기 - 2(= 8)개까지. 나머지 커넥션은 event·alarm·command 즉시 저장과 API용
  - 저장을 기다리는 행은 버퍼 하나에만 쌓인다. 그래서 B에서 상한을 걸 수 있다
- 종료할 때(MQTT가 닫힌 뒤, DB가 닫히기 전) 버퍼에 남은 행을 저장
  - 확인: 버퍼 300건, DB 0건인 상태에서 SIGINT → DB 300건
- event·alarm·cmd ack는 그대로 즉시 저장

### 효과
- **5,000 msg/s를 따라잡는다.** 기준선은 같은 부하에서 약 150초 만에 OOM으로 죽고 90 %를 잃었다
  - 처리량: 1건 INSERT의 상한(약 2,000~3,000 rows/s) → 5,000 rows/s 이상 (상한은 B 단계의 10,000/s에서 확인)
  - 5단계 flush 1,790번, 1번에 평균 500행. pg 풀 대기 최대 6
- 1000대 / 1000ms: 수신→커밋 p50 184 → 77 ms, p99 6.6 → 1.7 s. 1초에 한 번 오는 묶음 1,000건이 INSERT 2번으로 끝남
- 서버 CPU가 줄었다 (5단계: 기준선은 이미 막혀 있었지만 75 % → A 22 %). 1행마다 쓰던 쿼리 생성·Promise 오버헤드가 사라짐
- 행당 용량은 그대로 (5단계 +135.8 MiB / 900,000행 ≈ 158 B)

### 부작용
- **저부하 지연 증가**: 10대·100대에서 p50 10~23 ms → 약 210 ms. 배치가 차지 않으면 `FLUSH_MS`(200 ms)를 기다리기 때문. 처리량과 지연의 맞교환이다
  - 낮추려면 `FLUSH_MS`를 줄이면 된다 (예: 50 ms → p50 약 60 ms 예상, flush 횟수 증가). 관제 화면 갱신 주기(1초)보다는 짧다
- **서버가 죽으면 버퍼만큼 유실**: 정상 종료는 버퍼를 저장하지만, 강제 종료(SIGKILL·OOM)면 최대 `FLUSH_MS` 분량 + 저장 중인 배치를 잃는다
- 배치 하나가 실패하면 500행이 함께 실패한다 (형식 검증을 먼저 해서 실제로 일어날 일은 적음)
- **SQL Server 전환 시 주의**: SQL Server는 쿼리 1건당 파라미터 2,100개 제한. 1행이 8개라 `BATCH_SIZE` ≤ 260으로 줄이거나 나눠 보내야 한다

### 남은 병목 (A 이후)
- 버퍼에 상한이 없다. 처리 능력을 넘는 부하가 계속 오면 버퍼가 끝없이 커져 결국 OOM → 개선 B
- 3단계(500대)의 p99 수 초는 처리 능력 부족이 아니라 일시적인 멈춤이다. 버퍼 최대 1,500, 풀 대기 최대 91, postgres CPU 순간 996 %. 호스트·VM 쪽 원인으로 보고 계속 관찰

## 개선 B: 역압 (버퍼 상한)

### 무엇을 바꿨나
- 저장 대기 버퍼에 상한 `MAX_BUFFER`(기본 50,000행)를 둔다. 넘으면 `OVERFLOW_POLICY`에 따라 버린다
- 버린 건수는 `/metrics/ingest`의 `telemetry.dropped`에 남고, 10초 로그에 `역압 버림 N (누적 M)`으로 찍힌다
- 버퍼를 인덱스 기반 큐(`pending-queue.ts`)로 바꿨다. 앞에서 버리기가 O(1)이다 (`Array.shift`는 O(n))

### 상한을 넘을 때의 정책 비교

| 정책 | 동작 | 장점 | 단점 |
|---|---|---|---|
| **drop-oldest (선택)** | 가장 오래된 행을 버리고 새 행을 넣는다 | 저장되는 데이터가 최신에 가깝다. 버퍼에 머무는 시간이 짧아 지연이 낮다 | 과부하 구간의 과거 데이터에 구멍이 생긴다 |
| drop-newest | 새로 온 행을 버린다 | 이미 받은 행은 순서대로 모두 저장된다 | 과부하 동안 최신 상태가 늦게 보이고 새 값은 버려진다. 버퍼가 꽉 찬 채로 유지돼 지연이 가장 길다 |
| 수신 일시 정지 (MQTT 읽기 중단) | 소켓을 덜 읽어 브로커 쪽으로 밀어낸다 | 서버는 아무것도 버리지 않는다 | 텔레메트리 QoS 0이라 브로커가 조용히 버린다 (서버 지표에 안 잡힘). event·alarm·cmd ack도 같은 연결이라 함께 늦어진다 → 명령 타임아웃 위험 |

**drop-oldest를 고른 이유**
- 관제 시스템에서 가치가 큰 것은 지금 위성 상태다. 과부하 때 몇 초 전 값보다 최신 값을 살리는 게 낫다
- 지연이 더 낮다. 같은 과부하에서 수신→커밋 p50이 917 ms였다 (drop-newest는 1,417 ms)
- 버리는 위치가 서버 안이라 건수를 정확히 셀 수 있다. 수신 일시 정지는 브로커에서 버려져 셀 수 없다
- event·alarm·command는 버퍼를 거치지 않아 영향이 없다

**MAX_BUFFER = 50,000의 근거**
- 메모리: 버퍼 1행 ≈ 425 B (Node에서 같은 모양의 객체 10만 개로 측정) → 50,000행 ≈ 21 MiB. heap 한도(약 2 GB)의 1 %
- 흡수할 수 있는 멈춤: 측정 중 가장 긴 일시 멈춤은 약 7.5 s였다 (A 3단계 수신→커밋 max). 5,000 msg/s에서 7.5 s ≈ 37,500행 → 50,000이면 약 10초를 버틴다
- 정상 운영에서는 닿지 않는다: 10,000 msg/s에서도 버퍼 최대 4,500

|---|---|---|---|---|---|---|---|---|---|---|
| 1000대 / 1000ms | 1,000 → 994 | 77 / 204 / 1,694 / 3,286 → 71 / 157 / 285 / 582 | 0.07 → 0.11 s | 0 → 0 | 7.3 → 6.9 % | 195 → 202 MiB | 55 → 32 | 500 → 500 | 20 → 14 % | 통과 |
| 1000대 / 200ms | 4,988 → 4,919 | 43 / 77 / 164 / 682 → 50 / 376 / 1,140 / 3,046 | 0.05 → 0.05 s | 0 → 0 | 22 → 24 % | 230 → 218 MiB | 6 → 65 | 500 → 4,938 | 32 → 52 % | 통과 |

- 1000대 / 200ms의 p99가 A보다 크다 (164 → 1,140 ms). 역압은 이 부하에서 작동하지 않았다 (버림 0, 버퍼 상한의 10 %). 같은 코드 경로라서 일시 멈춤 때문으로 본다 (버퍼 순간 4,938, postgres CPU 순간 498 %)
- 2000대 / 200ms를 두 번 쟀는데 (drop-oldest / drop-newest) 둘 다 버림이 0이었다. 정책 차이가 아니라 실행마다 생기는 편차다 (p99 487 vs 129 ms)

### 역압 동작 확인 (일부러 과부하)
처리 능력을 기준선 수준으로 낮춰(`BATCH_SIZE=1` → 1건 INSERT) 과부하를 만들었다. `MAX_BUFFER=5000`, 1000대 / 200ms (5,000/s), 60초.

| 정책 | 받음 | 커밋 | 버림 | 저장/s | heap max | 버퍼 max | 수신→커밋 p50 / p99 / max (ms) |
|---|---|---|---|---|---|---|---|
| drop-oldest | 298,000 | 202,560 | 95,440 | 3,337 | 184 MiB | 5,000 | **917** / 1,186 / 1,452 |
| drop-newest | 298,000 | 200,232 | 97,768 | 3,326 | 177 MiB | 5,000 | 1,417 / 1,762 / 1,847 |

- **OOM 없음**: 같은 모양의 과부하에서 기준선은 heap 2 GB OOM으로 죽었다. B는 heap 180 MiB 안팎에서 멈췄다
- **건수가 정확히 맞는다**: 받음 = 커밋 + 버림. DB 행 수 = 커밋. 시뮬레이터 발행 - 저장 = 버림
- 10초 로그 예: `버퍼 4350 (저장 중 8) | 역압 버림 16638 (누적 22469) | 수신→커밋 p50 916.9ms`
- `BATCH_SIZE=10`으로는 과부하를 만들 수 없었다 (5,000/s를 그대로 따라잡음). 10건 배치만으로도 처리량이 충분하다는 뜻이다

### 부작용
- 처리 능력을 넘으면 데이터를 버린다 (의도된 동작). 기준선은 버리지 않는 대신 죽어서 90 %를 잃었다
- drop-oldest는 과부하 구간에 시계열 구멍이 생긴다. 조회·대시보드는 빈 구간을 표시해야 한다
- 정상 부하에서는 오버헤드가 없다 (버림 0, 상한 비교 1회뿐)

### 남은 병목 (A+B 이후)
- **10,000 msg/s까지 한계가 나오지 않았다.** 다음 측정에서 3000대 / 200ms 이상으로 올려 찾아야 한다
- 10,000 msg/s에서 가장 먼저 차오르는 것:
  - **서버 Node CPU**: 평균 37 %, 최대 97 %. 단일 스레드라 1코어 = 100 %가 상한. MQTT 수신·JSON 파싱·검증을 메시지마다 한다
  - postgres CPU: 평균 63 % (8코어 중 0.6코어)로 여유가 있다
  - pg 풀 대기 최대 330, 버퍼 최대 4,500. 일시적으로 쌓였다가 풀린다
- 예상 다음 병목은 서버 이벤트 루프(CPU). 풀 크기(C)는 풀 대기가 일시적으로만 생겨서 효과가 작을 것으로 예상한다. 측정으로 확인할 것
- 측정 환경 잡음: 호스트 메모리 압박(스왑 11~12 GB) 때문에 실행마다 p99가 수백 ms ~ 수 초 흔들린다. 비교는 p50과 처리량 위주로 하고, p99는 여러 번 재서 봐야 한다

## 개선 C: pg 커넥션 풀 크기

다음 작업으로 미룸 (풀 10 / 20 / 30 × 5단계 비교 예정).
- 할 일: `DB_POOL_SIZE` 환경변수 추가 (TypeORM `poolSize`, 동시 저장 수 = 풀 - 2), 3000대 / 200ms 이상 단계도 추가해 한계 찾기
