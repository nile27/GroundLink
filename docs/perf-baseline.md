# 새 기준선 (v2) — 2026-11-03

코드는 개선 전과 같다 (메시지 1건 = INSERT 1건, pg 풀 10). 측정 절차만 바꿨다.

- 단계마다 `telemetry`, `events`, `alarms`를 비우고 시작 (`RESET=1`). 테이블 크기가 결과에 섞이지 않게
- **수신→커밋 완료**: 서버가 INSERT 커밋 직후 직접 잰 지연 (`/metrics/ingest`). `inserted_at`(트랜잭션 시작)에서 빠지던 커밋·fsync 시간이 포함됨
- 한계 판정: "지연 계속 증가"는 마지막 30초 구간 3개가 연속으로 증가할 때만 (일시적 멈춤 1회는 제외)
- 환경은 v1과 같음 (M1 / 8 GiB, Docker Desktop CPU 8 · 3.83 GiB). 측정 중 호스트 스왑 사용량 11~12 GB로 메모리 압박이 있었다

## 한계 지점: 1000대 / 200ms (5,000 msg/s)

**처리 능력은 약 2,000 ~ 3,000 rows/s다.** 1,000 msg/s(4단계)는 따라잡았고 5,000 msg/s(5단계)에서 무너졌다.

5단계에서 일어난 일 (서버 프로브 기준, 발행 시작부터):

| 경과 | 서버 CPU | heap | pg 풀 (사용 / 대기) |
|---|---|---|---|
| 5 s | 66 % | 137 MiB | 10 / 3,794 |
| 20 s | 84 % | 509 MiB | 10 / 52,457 |
| 47 s | 95 % | 1,141 MiB | 10 / 156,668 |
| 75 s | 100 % | 1,724 MiB | 10 / 273,911 |
| 약 150 s | — | 2,040 MB | `FATAL ERROR: ... JavaScript heap out of memory` |

1. 저장 속도가 발행 속도의 절반 이하라서, 처리하지 못한 INSERT가 pg 풀 대기열에 초당 약 3,000건씩 쌓였다
2. 서버는 메시지마다 `handle()`을 호출하고 끝나기를 기다리지 않는다. 그래서 대기열에 상한이 없고 heap이 계속 커졌다
3. heap이 커지자 GC(Mark-Compact 한 번에 10~15초)가 CPU를 차지했고, 저장률이 2,033 → 459 rows/s로 떨어졌다
4. heap 한도(약 2 GB)에 닿아 서버 프로세스가 죽었다. 메모리 대기열에 있던 메시지와 그 뒤의 텔레메트리(QoS 0)가 모두 사라져 유실이 90 %가 됐다

## 병목 분석: 무엇이 먼저 막혔나

**먼저 막힌 것은 "INSERT 1건 = 트랜잭션 1건"이 pg 풀 10개로 처리할 수 있는 양이다.** CPU, DB 쓰기 대역폭, 이벤트 루프는 그보다 나중이다.

| 후보 | 판단 | 근거 |
|---|---|---|
| **커넥션 수 (pg 풀 10)** | **먼저 막힘** | 3~5단계에서 풀 10개가 모두 사용 중(idle 0)이고 대기가 쌓였다. 5단계는 대기가 계속 늘기만 했다. 1단계의 1건당 수신→저장 약 4 ms(+시계 차이 약 2 ms)와 풀 10개로 계산하면 상한은 약 2,000~2,500 rows/s. 관측 최대치(10초 평균 2,033, 1초 최대 3,215)와 맞는다 |
| DB 쓰기 / fsync | 원인의 일부 (1건당 왕복 시간에 포함) | `synchronous_commit=on`이라 커밋마다 WAL fsync를 기다린다. 4단계는 WAL sync 69,964회에 행 187,582개로, sync 1회당 약 2.7행(group commit)이다. postgres CPU 평균은 40 %(8코어 중 0.4코어)로 여유가 있었다. DB가 계산을 못 따라간 게 아니라 커밋 하나하나를 기다린 것이다 |
| 서버 CPU | 처음엔 아님 → 나중에 막힘 | 4단계 평균 14 %. 5단계는 시작 5~20초에 66~84 %였는데도 이미 대기가 쌓였다. 100 %가 된 건 heap이 커지고 GC가 늘어난 뒤다 (결과이지 원인이 아님) |
| 이벤트 루프 지연 | 처음엔 아님 | 1~4단계 p99 평균 12~18 ms. 5단계 초반 최대값은 30~100 ms로 정상이다. 이후 GC 때문에 5,318 ms까지 늘었다 |
| 브로커 (mosquitto) | 아님 | 5단계 CPU 평균 8 %, 최대 52 %, 메모리 3.7 MiB. 발행→수신 p99는 422 ms로 수신→저장(수십 초)에 비하면 무시할 수준 |
| 시뮬레이터 | 아님 | 5단계 CPU 평균 7.7 %. 발행률이 목표치(5,000/s)대로 나왔다 |

추가로 확인된 문제:

- **역압(backpressure)이 없다**: 처리 능력을 넘으면 느려지는 데서 그치지 않고 서버가 죽는다. 그러면 QoS 0 텔레메트리는 그대로 사라진다
- **4단계도 여유가 적다**: 수신→저장 p50이 134 ms인 이유는 시뮬레이터가 1초에 한 번 1,000건을 한꺼번에 보내기 때문이다. 이 묶음을 풀 10개가 비우는 데 수백 ms가 걸린다. 묶음 1개(1,000건)가 처리 능력의 1/2~1/3을 차지한다
- **측정 한계**: `inserted_at`(DEFAULT `now()`)은 트랜잭션이 *시작된* 시각이다. 커밋·fsync 시간은 "수신→저장"에 들어가지 않는다. 그래서 1건당 실제 처리 시간은 처리량에서 거꾸로 추정했다

## "지연 튐"이 부하에 따라 어떻게 변하나

e2e(발행→저장) 최대가 250 ms를 넘은 초를 셌다.

| 단계 | 튄 초 / 전체 | 양상 |
|---|---|---|
| 1. 10 msg/s | 0 / 179 | 기준선 측정 때(100초에 4번, 최대 1,072 ms)와 달리 이번에는 없었다. 최대 93 ms |
| 2. 100 msg/s | 4 / 179 | 08:32:21~23에 발행→수신이 333 ms까지 늘었다. **서버와 시뮬레이터 이벤트 루프가 같은 순간 함께 멈췄다** (각각 105 ms, 175 ms) |
| 3. 500 msg/s | 16 / 179 | 대부분 시작 60초 안에 몰렸다 (첫 주기의 새 위성 400대 등록, JIT 예열). 08:35:33~35는 수신→저장이 최대 1,994 ms였는데 같은 순간 서버 이벤트 루프 지연은 135 ms였다. **DB 응답이 멈춘 것**이다. 이 단계에서는 체크포인트가 없었다 |
| 4. 1,000 msg/s | 135 / 179 | 가끔 튀는 게 아니라 **계속 지연된다**. 1초마다 오는 묶음 1,000건이 풀에서 비워지는 시간(수백 ms)이 그대로 지연이 된다. 발행→수신 p99는 121 ms로 안정적 |
| 5. 5,000 msg/s | 19 / 19 | 쌓이는 대기열 때문에 수십 초 지연 |

해석:

- 부하가 낮을 때는 가끔 튀고, 원인이 프로세스 밖에 있을 가능성이 크다. 서로 다른 두 프로세스가 같은 순간 멈춘 것은 각자의 GC로 설명하기 어렵다. 호스트나 Docker Desktop VM이 잠깐 멈췄다고 보는 게 맞다. 수신→저장만 튄 경우는 DB 응답(VM 디스크 I/O·fsync)이 멈춘 쪽에 가깝다
- 체크포인트는 원인이 아니다. 1·2단계 체크포인트(08:28:18~26, 08:33:18~54)는 튄 순간과 겹치지 않는다(08:33:29의 277 ms 1건만 겹침). 3단계는 튄 일이 많았지만 체크포인트가 0회였다
- 부하가 오르면 원인이 "풀 대기"로 바뀌고, 지연이 일정하게 깔린다. 1,000 msg/s부터는 튐보다 묶음 처리에 걸리는 시간이 지배한다

## 용량 다시 계산

4단계 측정: 179,000행에 telemetry +27.6 MiB → **행당 약 160 B** (인덱스 포함). 기준선의 500 B/행은 행 수가 적어서 페이지 오버헤드가 컸던 값이다.

| 규모 | 하루 용량 (텔레메트리) |
|---|---|
| 10대 × 1초 | 약 140 MB |
| 1,000대 × 1초 | 약 14 GB |

## 개선 후보 (아직 적용 안 함)

| 우선순위 | 후보 | 예상 효과 | 비고 |
|---|---|---|---|
| 1 | **일괄 저장** (메모리 버퍼 → N건 또는 T ms마다 다중 행 INSERT 1건) | 처리량 수~수십 배 (커밋·왕복이 행 수만큼 줄어든다). 4단계의 묶음 지연 감소 | 직접 원인 해결. 크래시 때 버퍼(최대 T ms 분량)를 잃는다 |
| 2 | **역압 / 상한 있는 대기열** (처리 중 건수 상한, 넘으면 버리고 카운트 또는 MQTT 수신 일시 정지) | 과부하에서 OOM으로 죽지 않고, 정해진 만큼만 버린다 | 성능보다 안정성. 1번과 함께 |
| 3 | pg 풀 크기 조정 (10 → 20~30), 측정 | 1건 INSERT 구조에서도 상한이 거의 비례해서 오른다 (DB CPU 여유가 있음) | 근본 해결은 아님. 1번 뒤에 다시 측정 |
| 4 | 텔레메트리만 `synchronous_commit=off` (세션·트랜잭션 단위) | 커밋마다 fsync를 기다리지 않음 → 1건당 시간 감소 | DB가 죽으면 마지막 수백 ms가 유실될 수 있다. 텔레메트리는 감수할 만함 |
| 5 | 저장 경로에서 TypeORM `insert()` 대신 쿼리 빌더 / `RETURNING` 없는 INSERT | CPU·왕복 데이터 소폭 감소 | 효과는 작다 |
| 6 | 텔레메트리 QoS 1 + 서버 영구 세션(clean: false) | 서버가 재시작·장애를 겪어도 브로커가 메시지를 보관 | 신뢰성 개선. 브로커 메모리·디스크 사용 증가 |
| 7 | 시간 단위 파티션 / 보관 정책, 집계 테이블 | 1,000대 기준 하루 14 GB 문제 해결 | 용량·조회 성능. SQL Server 전환을 고려해 설계 |
| 8 | 시뮬레이터 발행을 주기 안에 고르게 분산 | 묶음 지연(4단계 p50 134 ms) 감소. 실제 위성 분포에 가까움 | 서버 개선이 아니라 측정 조건 변경. 비교 시 구분할 것 |
